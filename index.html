Why OpenSpot

Spend less time rebuilding the integration layer.

Field robotics teams repeatedly solve the same mechanical, power, networking, compute, calibration, and operator-interface problems before they can test a research idea.

OpenSpot is documenting one working reference system as reusable open hardware: modular sensor plates, onboard Jetson compute, a high-bandwidth payload network, and a forthcoming handheld operator stack.

Reference architecture

Robot-to-operator connectivity

Spot, compute, sensors, and the payload radio share a 2.5 GbE network. A point-to-point wireless bridge extends that network to the operator-side access point and handheld console.

The addresses and components shown are examples. The wireless bridge is not a safety channel, and published range, latency, and packet-loss validation is still pending.

What the project brings together

Modular hardware

Compute, LiDAR, radio, auxiliary electronics, and hot-swappable sensor mounts designed as one payload system.

Alpha CAD available

Edge compute

A Jetson Orin reference payload for perception, mapping, logging, and autonomy workloads close to the sensors.

Reference documented

Field networking

Onboard switching and a long-range wireless bridge connecting robot telemetry to the operator side.

Validation pending

OpenSpot Operator

A Steam Deck interface and Jetson daemon for control, telemetry, video, diagnostics, and mission supervision.

Roadmap

From prototype to reproducible field platform

01

Documented alpha

Inventory, scope, limitations, licensing, and reference architecture.

02

Reproducible hardware

Source CAD, drawings, BOM, electronics, assembly, and measured payload properties.

03

Software bring-up

Versioned deployment, packaged Operator, protocol tests, diagnostics, and recovery behavior.

04

Field validation

Repeatable network and mission tests, public logs, negative results, and an independent rebuild.

Build it with us
